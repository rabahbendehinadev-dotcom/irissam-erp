# إصلاح توليد MRN بشكل Atomic داخل PostgreSQL

الحل الحالي يستعمل:

`countAll()`

ثم يولد الرقم التالي داخل Transaction.

هذا غير آمن عند وجود طلبين متزامنين، لأن Transaction وحدها لا تمنع طلبين من قراءة نفس العدد قبل تنفيذ INSERT.

عبارة أن التعارض "مستحيل عمليًا" غير صحيحة في نظام مستشفى Production.

## المطلوب

استبدل توليد MRN الحالي بآلية Atomic حقيقية داخل PostgreSQL.

الحل المفضل:

* PostgreSQL Sequence مخصصة لأرقام المرضى.
* Migration جديدة فقط.
* ممنوع تعديل Migration قديمة.
* ممنوع استعمال `COUNT(*) + 1`.
* ممنوع استعمال `MAX(...) + 1`.
* ممنوع استعمال `Math.random()`.
* ممنوع استعمال Timestamp كمعرف طبي.

مثال منطقي:

```sql
CREATE SEQUENCE patient_mrn_sequence;
```

ثم داخل إنشاء المريض:

```sql
SELECT nextval('patient_mrn_sequence');
```

ومن نفس الرقم يتم توليد:

* `mrn`: `MRN-YYYY-00042`
* `mpiId`: `MPI-YYYY-00042`
* `fileNumber`: `YYYY-00042`

استعمل نفس قيمة `nextval()` مرة واحدة فقط لكل مريض.

## Unique Constraints

تحقق من قاعدة البيانات وأضف، عبر Migration جديدة إذا كانت غير موجودة:

* UNIQUE على `mrn`
* UNIQUE على `mpi_id`
* UNIQUE على `file_number`

قبل إضافة Constraints:

* افحص البيانات الحالية بحثًا عن duplicates.
* إذا وجدت تكرارًا، لا تحذف البيانات تلقائيًا.
* أعطني تقريرًا بها وطريقة آمنة لمعالجتها.

## توافق البيانات الحالية

يجب ألا تبدأ الـSequence من 1 بشكل أعمى.

احسب أكبر رقم مستخدم حاليًا داخل MRN، ثم اضبط الـSequence لتبدأ من الرقم التالي.

مثلًا إذا كان أكبر رقم:

`MRN-2026-00157`

يجب أن يكون الرقم التالي:

`158`

يجب أن تعمل أيضًا إذا كانت قاعدة البيانات فارغة.

## السنة

حدد بوضوح سلوك العداد عند تغير السنة:

### الخيار المفضل

عداد مستقل لكل سنة، مثل:

* 2026 يبدأ من 00001
* 2027 يبدأ من 00001

إذا كان تنفيذ Sequence منفصلة لكل سنة معقدًا، استعمل جدول Counter آمنًا يحتوي:

* year
* last_value

مع:

* Row lock
* `SELECT ... FOR UPDATE`
* Transaction
* Unique Constraint على year

لا تنشئ Sequence جديدة ديناميكيًا من اسم سنة بدون حماية أو Validation.

## اختبار التزامن الحقيقي

لا تكتفِ بالتحليل النظري.

نفذ اختبارًا يرسل على الأقل 20 طلب إنشاء مرضى بالتوازي.

تحقق من:

* 20 UUID مختلفة.
* 20 MRN مختلفة.
* 20 MPI IDs مختلفة.
* 20 File Numbers مختلفة.
* 0 Unique Constraint Violation.
* 0 Patients مفقودين.
* الأرقام قد تحتوي على gaps عند rollback، وهذا مقبول.
* لا يوجد Duplicate.

احذف بيانات الاختبار أو نفذ الاختبار داخل Database مخصصة للاختبار، وليس على بيانات Production الحقيقية.

## Duplicate Detection

راجع أيضًا أن Duplicate Check الحالي يستعمل مقارنة غير حساسة لحالة الأحرف.

حاليًا المقارنة موصوفة بأنها case-sensitive.

يجب أن يتعرف النظام على:

* `BENALI` و`Benali`
* المسافات الزائدة
* الحروف الفرنسية ذات الاختلافات البسيطة إن أمكن

طبّق Normalization مناسبًا على:

* firstName
* lastName

مثل:

* trim
* lower
* إزالة المسافات المكررة

لا تعتمد فقط على الاسم.

إذا كانت الحقول متاحة، حسّن ترتيب قوة التطابق:

1. رقم الهوية نفسه → تطابق قوي جدًا.
2. رقم الهاتف نفسه → تطابق قوي.
3. الاسم + اللقب + تاريخ الميلاد → تطابق قوي.
4. الاسم + اللقب فقط → تطابق محتمل، لا تمنع الحفظ تلقائيًا.

لا تعرض بيانات حساسة لا يملك المستخدم Permission لرؤيتها.
