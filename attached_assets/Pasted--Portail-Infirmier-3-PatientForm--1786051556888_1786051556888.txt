التقرير مليح، بصح مازال ما نبدأوش **Portail Infirmier** قبل ما نسدو 3 نقاط مهمة:

* `PatientForm` يولّد ID عشوائيًا في الواجهة.
* `checkDuplicates()` ترجع دائمًا `[]`، يعني كشف المرضى المكررين متوقف.
* الـProduction build الحقيقي والـDeploy على Dokploy مازال ما تأكدوش.

ابعث له هذا البرومبت:

ممتاز. إزالة الـMock Data تمت بنجاح، لكن لا تبدأ Portail Infirmier بعد.

بقيت آخر مرحلة تحقق قبل إغلاق Production Hardening رسميًا.

# المهمة: إصلاح إنشاء المرضى وكشف التكرار والتحقق من Production Build

## أولًا: PatientForm — منع توليد Patient ID عشوائيًا

حاليًا تم استبدال الاعتماد على `MOCK_PATIENTS.length` بتوليد رقم عشوائي داخل الواجهة.

هذا غير مقبول في Production، لأنه قد يسبب:

* Duplicate Patient IDs.
* تعارضًا بين المستخدمين.
* اختلافًا بين Frontend وPostgreSQL.
* مشاكل عند إنشاء مريضين في نفس الوقت.

## المطلوب

ابحث عن الطريقة الحالية التي ينشئ بها Backend المريض.

يجب أن يكون:

* `id` الأساسي مولدًا من PostgreSQL أو Backend.
* رقم الملف الطبي `patient_number` أو `medical_record_number` مولدًا مركزيًا من Backend.
* لا يتم توليد أي معرف نهائي للمريض داخل React.

إذا كانت API إنشاء المريض تولد الرقم تلقائيًا:

* احذف توليد الرقم من Frontend.
* لا ترسل الحقل إلا إذا كان Backend يطلبه فعلًا.
* استعمل الرقم الذي ترجعه API بعد نجاح الإنشاء.

إذا لم يوجد توليد مركزي لرقم الملف الطبي:

* لا تستعمل `Math.random()`.
* أضف توليدًا آمنًا داخل Backend فقط.
* استعمل Transaction أو Sequence أو آلية PostgreSQL تمنع التكرار.
* أضف Unique Constraint إذا لم يكن موجودًا.
* لا تعدل Migration قديمة؛ استعمل Migration جديدة فقط عند الضرورة.

تحقق من عمليات:

* إنشاء مريض جديد.
* إنشاء مريضين في نفس الوقت.
* إعادة المحاولة بعد Network Error.
* تعديل المريض دون تغيير رقمه.
* عدم إنشاء سجلين لنفس الطلب.

# ثانيًا: إعادة تشغيل كشف المرضى المكررين

حاليًا:

`checkDuplicates()` ترجع دائمًا `[]`.

هذا يعني أن النظام توقف عن كشف التكرار، وهو خطر على بيانات المرضى.

لا أريد Mock ولا نتيجة ثابتة.

## المطلوب

ابحث أولًا داخل Backend عن API أو Query موجودة لكشف المرضى المتشابهين.

استعمل الحقول الحقيقية المتاحة، مثل:

* رقم الهاتف.
* رقم الهوية.
* الاسم واللقب.
* تاريخ الميلاد.
* الجنس.
* البريد الإلكتروني.
* رقم التأمين.
* رقم الملف الطبي.

إذا كانت API موجودة:

* اربط `PatientForm` بها.
* استعمل Debounce مناسب.
* لا ترسل Request عند نقص البيانات الأساسية.
* اعرض النتائج المحتملة قبل إنشاء المريض.
* اسمح للمستخدم بفتح ملف المريض الموجود بدل إنشاء نسخة جديدة.

إذا لم توجد API مخصصة:

* ابحث عن API قائمة المرضى أو Search الموجودة وأعد استعمالها إذا كانت كافية.
* لا تنشئ Endpoint جديدًا إلا إذا لم توجد طريقة صحيحة وآمنة بالموجود.

## سلوك الواجهة المطلوب

إذا لم يوجد تطابق:

* السماح بالحفظ طبيعيًا.

إذا وجد تطابق محتمل:

* عرض قائمة واضحة بالمرضى المتشابهين.
* إظهار الاسم، تاريخ الميلاد، الهاتف، ورقم الملف.
* توفير زر لفتح المريض الموجود.
* طلب تأكيد واضح قبل الاستمرار في إنشاء مريض جديد.
* لا تستعمل `alert()`.

إذا فشل فحص التكرار بسبب API Error:

* لا تتجاهل الخطأ بصمت.
* اعرض رسالة واضحة مع Retry.
* لا تدّعِ أنه لا توجد نتائج.

# ثالثًا: مراجعة الـSilent Failures الجديدة

راجع جميع الملفات التي تم تعديلها لإزالة Mock Data.

ابحث خصوصًا عن:

* `catch {}` فارغ.
* `catch(() => {})`.
* فشل Fetch صامت.
* `return []` كحل مؤقت.
* `return null` غير مغطى بحالة UI.
* Random IDs.
* Placeholder IDs.
* بيانات ثابتة مؤقتة.

بالنسبة إلى:

* ConsultationHeader
* ConsultationReport
* ConsultationWorkspace

إذا كان Fetch الخاص بالبيانات التكميلية يفشل:

* لا تسبب White Screen.
* يمكن عرض البيانات الأساسية.
* لكن سجل الخطأ بشكل مناسب أو اعرض حالة غير مزعجة إذا كانت المعلومة مهمة طبيًا.
* لا تعرض معلومة فارغة على أنها مؤكدة طبيًا.

# رابعًا: Frontend Production Build حقيقي

تشغيل Vite dev server لا يعتبر Production Build.

نفذ نفس أمر البناء الموجود في Dockerfile مع نفس المتغيرات المطلوبة.

حدد أولًا القيم التي يحتاجها البناء، مثل:

* `PORT`
* `BASE_PATH`
* أي VITE environment variables

ثم نفذ Production Build فعليًا.

يجب أن تكون النتيجة:

* Build ناجح.
* ملفات `dist` مولدة.
* 0 TypeScript Errors.
* 0 Build Errors.
* 0 Missing Imports.
* 0 Dev-only Routes داخل Bundle.
* 0 MockRepository داخل Bundle.
* 0 MOCK_PATIENTS داخل Bundle.

لا تغير الـDockerfile فقط لكي ينجح الاختبار إذا كان يعمل حاليًا في Dokploy.

# خامسًا: GitHub وDokploy

بعد الانتهاء:

1. أنشئ Commit مستقلًا لهذه الإصلاحات.
2. أخبرني بآخر Commit Hash.
3. لا تقل إن Production تم التحقق منها ما دام Push وDeploy لم يتما.
4. أعطني أمر أو خطوات التأكد أن:

   * `origin/main` يحتوي آخر Commit.
   * Dokploy بنى نفس Commit.
   * Container الحالي يشغل نفس الإصدار.

# التقرير النهائي المطلوب

أعطني:

1. كيف أصبح Patient ID يُولّد.
2. كيف أصبح رقم الملف الطبي يُولّد.
3. هل يوجد Unique Constraint؟
4. كيف يعمل كشف المرضى المكررين؟
5. ما هي الحقول المستعملة في المقارنة؟
6. ماذا يحدث عند فشل Duplicate Check؟
7. هل بقي أي Random أو Placeholder ID؟
8. نتيجة اختبار إنشاء مريضين متزامنين.
9. نتيجة TypeScript.
10. نتيجة Backend Build.
11. نتيجة Frontend Production Build الحقيقي.
12. نتيجة فحص Production Bundle.
13. آخر Commit Hash.
14. هل تم Push إلى GitHub؟
15. هل تم Deploy على Dokploy؟

لا تبدأ Portail Infirmier داخل هذه المهمة.

لا نغلق Production Hardening رسميًا إلا بعد:

* عدم وجود Random Patient ID.
* Duplicate Detection حقيقي.
* Production Build ناجح.
* Push GitHub ناجح.
* Deploy Dokploy ناجح.
* Smoke Test ناجح على الدومين.

بعد ما يكمل هذا، عاود اربط GitHub، دير Push وDeploy، وبعدها جرّب إنشاء مريض جديد في الموقع الحقيقي. إذا كل شيء نجح، نبدأ Portail Infirmier رسميًا.
